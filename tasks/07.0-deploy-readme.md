# Task 7.0: Deploy and README

Publish the site and write a README that a non-technical visitor understands. Do after step 6 (Lighthouse included), so the screenshots show the final site.

Repo: https://github.com/Kotkoa/miss-cupcake (public). Figma: https://www.figma.com/design/cdK7lnOsfixA9OqNe17CrJ/Miss-Cupcake-Prototype--Copy-?node-id=0-1

## 1. Hosting: GitHub Pages first, Vercel as fallback

**GitHub Pages** (`https://kotkoa.github.io/miss-cupcake/`) via GitHub Actions (`.github/workflows/deploy.yml`: install → `yarn test` → `yarn build` → `actions/deploy-pages`). It is an SPA under a sub-path, so:

- `vite.config.ts`: `base: '/miss-cupcake/'` (only for the Pages build, e.g. via an env variable, so `yarn dev` keeps `/`).
- `BrowserRouter basename={import.meta.env.BASE_URL}`.
- Every hard-coded root path must respect the base: e.g. the video `src="/media/our-story.mp4#t=0.1"` → `${import.meta.env.BASE_URL}media/...`. Grep for `"/` and `'/` in `src/` and fix all asset paths (route links via `<Link>` are fine).
- Deep links (`/miss-cupcake/checkout` opened directly or reloaded): GitHub Pages has no rewrites. Copy `dist/index.html` to `dist/404.html` in the build step so every route boots the app.

**Switch to Vercel** if one of these is true, and note which one in the Test report:
- the 404.html fallback breaks something you can't fix (e.g. Lighthouse SEO drops because deep links return HTTP 404),
- assets under the sub-path can't all be fixed cleanly.

Vercel: import the repo, framework Vite, `vercel.json` with a rewrite of all paths to `/index.html`, base stays `/`.

Afterwards: `gh repo edit Kotkoa/miss-cupcake --homepage <live URL> --description "..." --add-topic react,vite,typescript,css-modules,jotai,figma-to-code`.

## 3. README

Model: readable intro like [rickandmorty](https://github.com/Kotkoa/rickandmorty), screenshot table and "How to run" like [DigtAG-SpaceX-Explorer](https://github.com/Kotkoa/DigtAG-SpaceX-Explorer). Plain English, short sentences; technical details only in the last sections.

Structure:

1. **Title + one sentence**: what it is ("A cupcake shop website built from a Figma design: browse cupcakes, fill a bag, and go through a full checkout").
2. **Links**: Live site, Figma design, Repository.
3. **What you can do here** (for non-technical readers, 4–6 bullets): browse the cupcakes, add them to the bag, check out and pay (demo: no real payment, nothing is sent), read the story, watch the video, find the store on the map, subscribe to the newsletter; works on phone, tablet and desktop; usable with a keyboard and screen reader.
4. **Screenshots**: table, 2–3 columns, caption above each image, `alt` text for each.
5. **How it was built** (short, why not how): React + Vite + TypeScript, React Router, CSS Modules with design tokens from Figma, Jotai for the bag, plain TypeScript form validation, Vitest. One line each, why it was chosen. Link to `tasks/` for the step-by-step plan and ADRs (`tasks/05.0-architecture.md`).
6. **Run it locally**:
   ```bash
   git clone https://github.com/Kotkoa/miss-cupcake.git
   cd miss-cupcake
   yarn
   yarn dev      # http://localhost:5173
   yarn test     # unit tests
   yarn build    # production build
   ```
7. **Credits**: design (the Figma file is a copy of a prototype: credit the original designer if the file names one), video (Pixabay, from `CREDITS.md`), map (© OpenStreetMap contributors), fonts (Wendy One, Lato).

## Test report

2026-10-13.

**Host: GitHub Pages** (`https://kotkoa.github.io/miss-cupcake/`), Vercel was not needed. The first deploy used the `404.html` copy only, as planned, and that is exactly the Vercel trigger in section 1: deep links (`/our-story`, `/checkout/payment`, ...) were answered with HTTP 404, and Lighthouse could not audit them at all (every category 0, the run errors on a 404 main document); crawlers treat them as broken pages too. It was fixable on Pages, so the fix went in instead of switching: `scripts/pages-fallback.mjs` copies the app shell into a folder per route after the build (`our-story/`, `why-miss-cupcake/`, `checkout/`, `checkout/payment/`), so those URLs are real files. Result (curl): `/` 200; `/our-story` 301 to `/our-story/` then 200 (same for the other three routes); an unknown path such as `/nope` 404 with the app's own "Page not found" page, which is the right status for a missing page. In-app links point to the slash form (`appHref`), so a click does not pay the redirect.

**Changes:** `vite.config.ts` `base` from `BASE_PATH` (default `/`, so `yarn dev` is untouched: checked, `/` and `/our-story` answer 200 and serve `main.tsx`); `BrowserRouter basename={import.meta.env.BASE_URL}`; `appHref()` puts the base in front of every plain `<a href>` (Button, header, footer; unit-tested); the video `src` uses `BASE_URL`; `build:pages` script; `.github/workflows/deploy.yml`; GitHub Pages enabled with `gh api -X POST repos/Kotkoa/miss-cupcake/pages -f build_type=workflow`. Everything else (fonts, images, CSS `url()`, the favicon and the font preload in `index.html`) is rewritten by Vite itself. A base-path build was first tried on a local server that mimics Pages (files, folder fallback, `404.html`): all routes direct and after reload, 0 links without the base, video, map image and 4 fonts load.
