# Task 6.3: Form errors

Two forms exist: Payment (5.5, already validates) and the footer newsletter (6.1). Figma shows only one error-like element: the note "* Must be 10 or more characters" under Passcode. This task makes errors consistent, readable and accessible across both forms.

## Rules

- **One error look**, in the shared `Input`: error text under the field (same position as the Passcode note), the field's outline in an error style, and an icon or "Error:" prefix so color is not the only signal (WCAG 1.4.1). Error color is a token (`--color-error`) with ≥ 4.5:1 contrast on cream and on purple (footer).
- **Hints vs errors:** the Passcode note is a hint (always visible, linked with `aria-describedby`); when invalid, the error replaces the hint visually but both stay announced.
- **Timing:** validate on blur and on submit (ADR-4); once a field has shown an error, re-validate it on every change so the error disappears as soon as it's fixed (no waiting for blur).
- **Submit with errors:** focus the first invalid field (done in 5.5) and announce the count once in a polite live region above the submit button: "3 fields need attention".
- **Messages:** short, say how to fix it, no blame. Review all texts in `validation.ts` against the table in 5.5; fix grammar per ADR-6.
- No error on fields the user hasn't touched before the first submit.

## Acceptance criteria

- [x] `Input` has one error style used by both forms; error color is a token with ≥ 4.5:1 contrast on every background it appears on (cream, purple); not color-only.
- [x] Passcode hint is visible before any interaction and linked via `aria-describedby`; when invalid, the screen reader reads the error and the hint.
- [x] After a field shows an error, typing a valid value removes the error immediately.
- [x] Empty submit on Payment: errors on all required fields, focus on First name, a single polite announcement with the count; no errors on untouched fields before that.
- [x] Footer newsletter shows the same error style on the purple band.
- [x] All error messages listed in this file (field → message) after review.
- [x] Unit tests updated for any changed message or rule.
- [x] Manual test (agent, Chrome at 375 / 1440, plus VoiceOver or NVDA if available, otherwise the Accessibility tree in DevTools): empty submit, fix one by one, newsletter invalid/valid; **Test report** appended.
- [x] `yarn build`, `yarn lint`, `yarn test` pass.

## What was built

- **One error look in `Input`** (both forms): the text under the field with a 16px icon (`assets/icons/error.svg`, used as a mask so it takes the text color), bold weight, and the field outlined in the error color (border + 2px inner ring, so it also reads on the 1px Mobile border). Not color-only: icon, weight, `aria-invalid`.
- **Error color is two tokens, not one.** No single color reaches 4.5:1 on both a light and the purple surface (searched the whole RGB cube in steps of 5: the best single color reaches 2.65:1 against cream + peach + purple). So, like the focus ring, one per surface: `--color-error: #B00020` on cream 6.43 / peach 5.80 / pink 5.19, and `--color-error-on-dark: #FFB4AB` on the purple band 5.23 and bar 5.24. `Input` picks by tone (`default` / `light`). This deviates from the single-token wording of the task.
- **Hint vs error:** the hint is visible by default; while there is an error it is visually hidden (still in the DOM) and `aria-describedby` lists the error first, then the hint.
- **Timing:** blur and submit validate (Payment, and now the footer too). A field that has shown an error is re-validated on every change (`revalidateChanged` in `validation.ts`), also when it turns invalid again; the expiration month and year are checked together. Fields never validated stay quiet until blur or submit. The Payment error state (`errors`, `shown`, `attention`) is one pure reducer, `features/checkout/errorState.ts`, with tests.
- **Submit with errors:** focus goes to the first invalid field (as before). Above "Place order": a visible count that follows the fixes (`aria-hidden`) and a visually hidden `role="status"` that says "N fields need attention" once, on submit, and does not repeat while fields are fixed. The visible count only appears after a submit.
- **Footer:** `Footer` takes a `validate` prop (the shared `validateEmail`), validates on blur, re-validates on change once an error has shown; submit still goes through the newsletter hook.

## Code review (fixed)

- **Enter in any field wiped the errors of the submit** (the submit moves focus to the first invalid field, which fires a blur in the same event, and the blur handler built on the pre-submit render). Reproduced with a real Enter keypress in CVV on the empty form: only `cvv` was invalid. The error state is now a reducer (`errorState.ts`), every action builds on the state it is given; re-checked with the same keypress: 14 errors, focus on First name, count "14 fields need attention". Regression test: `submit` followed by a `blur` of another field keeps all 14.
- **Stale count came back:** after fixing everything and breaking one field the announcement said "14 fields need attention". `attention` is now cleared when no error is left (tested; checked in Chrome: `J` after all fixed gives one error, no count, no announcement).
- **Footer after a valid sign-up by Enter** (on Home the footer stays mounted and the input kept focus): the next blur validated the reset, empty field and flagged the sign-up that worked. The input is blurred before `reset()`; checked: no error after Enter.
- **Footer "shown once" rule:** it re-validated only while an error was visible; now it keeps checking on every change after the first error (checked: `bad` -> error, `ok@example.com` -> clear, `ok@` -> error at once).
- A second submit with the same count is not announced again (same text); the focus move to the first invalid field answers it. Kept on purpose, noted in the code.
